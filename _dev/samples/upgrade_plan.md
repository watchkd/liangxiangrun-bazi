## 二、四个结构性问题

### 问题一（P0）来源结构倒置：讲课抽了，办案没抽

字幕是**讲课**，批命书是**办案**。

讲课给的是原则与例外，讲的时候会把话说满、会说「一般来说」；
办案给的是**次序、分寸、落断的口气**——同一组四柱，先看什么后看什么，断到什么程度收住。

现在 98.5% 是讲课。所以输出必然像「条文罗列」，不像「批命」。

## 四、一条工程建议：把「条件」变成可计算的

`条件允许` 395 条不是缺陷。缺陷是**条件不可算**，于是「要不要用」全推给用户，检索结果只能并列。

**不要**把状态改成 `允许` 来让输出更像断语——那是伪造确定性，违反本包立身之本。

**要**给每条规则加一个 `trigger_check` 字段，用四柱结构可计算的条件表达：

```
trigger_check:
  - "month_branch in {亥,子,丑}"          # 夏冬生人
  - "day_master in {庚,辛}"                # 日主限定
  - "pillar_branches ∩ {临官,帝旺} = ∅"    # 十干败亡运的前提
  - "day_branch == 日主之墓"               # 墓库运
```

机器跑三态，输出改成：

```
条件：成立 3 ／ 不成立 5 ／ 无法判定 7
```

这样 395 条仍然「条件允许」，但用户看到的是**已经替他核过条件**的结果，而不是一堆要他自查的条文。

这是**唯一一条能让「引文库」变成「判断库」而不牺牲证据标准的工程改动**。

## 六、一个命学层面的判断

梁氏批命的分水岭，**不在「用神取谁」，在「先看什么、后看什么」**。

同一组四柱，次序一换，断语相反。上一轮那个 庚戌 日的例子就是现成的：
先看身强弱 → 亥月庚金泄气 → 「身弱不能托财官」→ 断成一生劳碌；
先看调候 → 冬生不问强弱 → 「丁丙为调候」→ 断成有救、只是财宜迟。

**同一个八字，两套断语，差别只在第一步看什么。**

所以这个包最值钱的资产，不是 411 条规则，而是 `pijing_method.md` 里那张次序表。

抽书时应当**先抽次序，再抽断语**。次序抽错，断语抽一万条也是散的。
